 01. Introduction

Project Introduction

This project implements a production-grade automated testing suite for a modern e-commerce application. By replacing manual regression checks with smart, self-synchronizing browser code and direct backend API queries, we guarantee application reliability, consistent checkout performance, and stable production deployments.

🛍️

What We Are Testing

• User registration, login states, and session storage persistence.
• Catalog traversal, price/image assertions, and AJAX filter operations.
• Multi-item cart additions, quantity subtotal updates, and billing forms.
• Direct orders placement, receipt ID parsing, and backend database parity.

💡

Key Project Ideas

• Automated Actions: Standardized operations on buttons and text boxes.
• No Random Failures: Explicit waits protect against flaky timeouts.
• Double Verification: Visual UI checks validated alongside raw REST API calls.

 02. Problem Statement

Why We Need Automated Testing

⏱️

Manual Testing Takes Too Long

Clicking filter checkboxes, filling out checkout forms, and matching cart totals manually on every release is slow, repetitive, and highly prone to human error.

🌀

Slow Page Loading & Race States

Asynchronous AJAX content updates dynamically. Standard test scripts fail randomly when trying to interact with elements that have not yet loaded on the screen.

🕸️

Hidden Backend Issues

Testing only visual elements misses severe backend drops. A product database or authorization server crash can go undetected without direct API status assertions.

📉

No Reports or Diagnostic Details

When failures occur, debugging without automated console logs, step timelines, or exact failure screenshots forces developers to waste hours reproducing issues.

 06. Design Pattern

Page Object Model (POM) Design

BasePage & Common Actions

Centralized file base_page.py contains reusable commands wrapped inside explicit waits (no static sleeping):

  • click(locator): Waits for element to become clickable before trigger.
  • enter_text(locator, text): Waits for visibility, clears input, and types.
  • js_click(locator): Bypasses headless overlay click limitations via JavaScript.

Separation of Pages & Locators

• Locators: Separated file stores IDs and XPATHs (e.g. product_locators.py).
• Page Objects: Page classes store business actions using those locators.
• Benefit: UI layout updates only require editing the locator file; all test cases keep working.

 08. BDD Implementation

BDD Implementation (Pytest-BDD)

English Feature Files & Step Mappings

• Gherkin files: Tests defined using Given, When, Then syntax (e.g. product_filter.feature).
• Context Fixtures: Fixtures inject driver context and share data (like initial item count) between step definitions.
• Marking: Annotation tags (@filter, @positive) run subsets of tests selectively in CI pipelines.

Exact Gherkin Filtering Scenarios

@filter @negative
Scenario: Incompatible filters
  When the user selects the "Footwear" filter checkbox
  And the user selects the "Red" filter checkbox
  Then no products should be displayed in the list

 13. How to Run

Setup Instructions & CLI Commands

Setup Instructions

1. Clone repository from GitHub:
git clone https://github.com/L1QU1D26/BUG-Busters-E2E-Automation-Framework.git
2. Create virtual environment:
python -m venv venv
3. Activate environment:
venv\Scripts\activate (Windows) or source venv/bin/activate (Linux/Mac)
4. Install libraries:
pip install -r requirements.txt

CLI Execution Commands

  • Run all tests (Headed):
    pytest -v
  • Run all tests (Headless):
    pytest -v --headless=true
  • Run only positive test scenarios:
    pytest -m positive
  • Run REST API layer tests:
    pytest tests/test_api.py
  • Run & compile HTML report file:
    pytest --html=reports/report.html
  • Launch Allure Dashboard:
    allure serve reports/allure-results
